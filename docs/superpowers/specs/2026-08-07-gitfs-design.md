## 1. Назначение и границы

Кроссплатформенный виртуальный файловый слой поверх git-репозитория. Монтирует
репозиторий как том (Windows — буква диска, Linux/macOS — точка монтирования), в
котором **история представлена деревом папок**: ветки, теги, коммиты и даты — это
директории, а отдельный файл можно открыть как папку со всеми его версиями.

Формулировка для README:

> Монтирует git-репозиторий как диск. Коммиты — папки. Файл — тоже папка, внутри
> все его версии.

**Целевой сценарий.** Посмотреть, чем был файл три месяца назад, не делая
`checkout`, не трогая рабочую копию и не выходя из привычного инструмента —
Проводника, Far, IDE, `grep`, Word.

**Нецелевые сценарии.** Редактирование истории. Работа как с рабочей копией.
Замена git. Сетевой доступ к удалённым репозиториям.

**Инвариант, который держит весь проект:** gitfs **никогда не пишет в
репозиторий** и никогда не выполняет код из репозитория (в том числе хуки, в том
числе `git`-бинарник в продакшн-пути). Это одновременно гарантия безопасности и
упрощение архитектуры — на всём пути чтения нет ни одной мутирующей операции.

## 2. Ключевые решения

| Решение | Выбор | Обоснование |
|---|---|---|
| Модель дерева | гибрид: пять вьюх в корне | самая выразительная; `history/` — лицо проекта |
| Семантика записи | copy-on-write overlay, в репозиторий не попадает | жёсткий read-only ломает Word, Excel и часть IDE, которые пишут lock-файлы рядом с открываемым файлом |
| Платформы | Windows + Linux + macOS | macOS — experimental, см. §20 |
| Windows-адаптер | WinFsp | буква диска, зрелый .NET-биндинг, семантика близка к FUSE |
| Доступ к git-объектам | собственный managed-ридер | ноль нативных зависимостей на трёх ОС, полный контроль над кэшем, и это главная инженерная ценность проекта |
| Формат хеша | SHA-1 | SHA-256-репозитории определяются и отвергаются с внятной ошибкой |
| Модель снапшота | иммутабельный `RepoSnapshot`, подменяется атомарно | даёт lock-free чтение при конкурентных вызовах ФС |

## 3. Пользовательская модель: дерево

```
<mount>/
├─ branches/
│   ├─ main/                        рабочее дерево ветки
│   └─ feature/login/               слэш в имени ветки → вложенная папка
├─ tags/
│   └─ v1.0/
├─ commits/
│   └─ a3f9c21/                     см. §3.2
├─ dates/
│   └─ 2026-08-07/                  состояние на конец дня
├─ history/
│   └─ src/Program.cs/              файл стал папкой
│       ├─ 0001-a3f9c21.cs          0001 — самая свежая версия
│       ├─ 0002-8b04e77.cs
│       └─ latest.cs
└─ .gitfs/
    ├─ status.txt
    ├─ log.txt
    └─ overlay/
```

Набор вьюх задаётся ключом `--views`; любую можно отключить.

### 3.1 Именование в `history/`

Версии именуются `NNNN-<short-sha><оригинальное расширение>`:

* порядковый номер спереди — сортировка по имени в Проводнике совпадает с
  хронологией (0001 = самая свежая);
* short-sha (7 символов, расширяется при коллизии) — копируется в `git show`;
* исходное расширение сохранено — работают подсветка синтаксиса и файловые
  ассоциации.

В папку попадают только те коммиты, где файл **действительно менялся** — то есть
OID блоба отличается от OID в предыдущем рассмотренном коммите. Коммиты, не
затрагивающие файл, пропускаются.

`latest.<ext>` — алиас на версию из текущей опорной точки; при обычном состоянии
репозитория это тот же объект, что и `0001-…`.

**Опорная история.** `history/` и `dates/` считаются обходом по первому родителю
**от текущего HEAD**. Следствие, которое надо помнить: файл, менявшийся только в
невлитой ветке, в `history/` не появится — его версии доступны через
`branches/<ветка>/` и `commits/<sha>/`. Опция `--history-ref <ref>` задаёт другую
опорную точку.

**Путь, который был и файлом, и директорией.** Редкий, но возможный случай: по
пути `src/Program.cs` когда-то лежала директория. Такой узел в `history/`
показывает и версии файла, и дочерние записи одновременно; при конфликте имён
применяется правило §3.3.

**Потолок.** Список ревизий обрезается по `--history-limit` (по умолчанию 500).
Факт обрезания отражается записью `.truncated` в директории и строкой в
`.gitfs/log.txt` — молчаливое усечение недопустимо.

### 3.2 Листинг ≠ резолв пути

Принцип, снимающий проблему объёма: **перечисление директории и разрешение пути —
разные операции.**

* `commits/` при листинге отдаёт последние N коммитов от опорной точки
  (по умолчанию 200, ключ `--commit-limit`).
* Путь `commits/<sha>/…` резолвится **всегда**, для любого валидного OID — полного
  или префикса от 7 символов, — даже если его не было в листинге.

Аналогично `dates/` перечисляет только дни, где были коммиты, а `history/<путь>/`
считает список ревизий лениво.

Модель заимствована у `/proc`: видно не всё, доступно всё. Это документируется в
README как осознанное поведение.

### 3.3 Конфликты имён

Три случая, где git допускает то, чего не допускает целевая ФС. Все три требуют
явного разрешения, иначе дерево окажется невоспроизводимым.

**Недопустимые символы.** git разрешает в именах `: * ? " < > | \` (полный
набор запрещённых печатных символов NTFS — девять, включая обратный слэш),
управляющие символы, а также завершающие точку и пробел. Каждый такой символ
заменяется на `%XX` (percent-encoding по коду). Сам символ `%` экранируется как
`%25`, поэтому преобразование обратимо. `/` в корректных git-деревьях
невозможен и отвергается при разборе объекта дерева.

**Юникод-нормализация.** NFC- и NFD-формы одного имени (`é` = U+00E9 и
`e`+U+0301) — разные записи git-дерева, но один файл для macOS. Политики со
свёрткой регистра сравнивают имена в нормализованной форме NFC — такая пара
получает суффикс `~2` как обычная коллизия регистра. Имена, не являющиеся
валидным UTF-8, в v1 не различаются после замены невалидных
последовательностей (U+FFFD) — зафиксированное ограничение.

**Зарезервированные имена.** `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`,
`LPT1`–`LPT9` — в любом регистре и с любым расширением. К основе имени
добавляется суффикс `%RES`: `aux.c` → `aux%RES.c`.

**Коллизия регистра.** git различает `README` и `readme`, Windows и macOS — нет.
Первый в порядке обхода сохраняет имя, последующие получают суффикс `~2`, `~3`.
Порядок детерминирован: git хранит записи дерева отсортированными (по имени, с
директориями, сравниваемыми как если бы к ним был приписан `/`), поэтому
результат воспроизводим между запусками и между машинами.

**Политика применения.** Ключ `--name-policy`:

* `native` (по умолчанию) — правила применяются там, где их требует платформа:
  на Windows все три, на Linux ни одного, на macOS только коллизия регистра;
* `portable` — правила Windows применяются всегда, поэтому дерево выглядит
  одинаково на всех трёх ОС. Нужен, когда смонтированное дерево сравнивают между
  платформами или синхронизируют.

Преобразования применяются **только к отображаемому имени**; для чтения объекта
используется исходный путь из git.

### 3.4 Метаданные

| Атрибут | Значение |
|---|---|
| Время изменения / создания | дата коммита (committer date), к которому относится узел |
| Время изменения для `history/NNNN-…` | дата коммита именно этой ревизии |
| Время для корней вьюх | дата коммита опорной точки |
| Размер файла | точный размер распакованного блоба, см. §6.4 |
| Атрибут «только чтение» | выставлен на всех узлах, не перекрытых overlay |
| Метка тома | `gitfs: <имя репозитория>` |
| Ёмкость тома | суммарный размер `.git/objects`; свободно — 0 |

Времена — не косметика: благодаря им сортировка Проводника по дате даёт
хронологию, а инструменты, сравнивающие метки времени, ведут себя осмысленно.

### 3.5 Особые типы записей

| Режим git | Представление |
|---|---|
| `100644`, `100755` | обычный файл; бит исполнения переносится на POSIX, на Windows игнорируется |
| `120000` (симлинк) | на Linux/macOS — настоящая символическая ссылка (`readlink`); на Windows — обычный файл с содержимым-целью и пометкой в `.gitfs/log.txt`, потому что создание симлинков требует привилегии или режима разработчика. Ключ `--symlinks=text\|reparse` оставлен на будущее |
| `160000` (gitlink, submodule) | пустая директория с файлом-маркером `.gitfs-submodule`, внутри — OID и путь |
| pointer-файл Git LFS | отдаётся как есть, без гидрации; факт отмечается в `doctor` |

## 4. Грамматика путей и разрешение

```
path      := "/" | "/" view [ "/" rest ]
view      := "branches" | "tags" | "commits" | "dates" | "history" | ".gitfs"

branches  := ref-name "/" tree-path        ; ref-name может содержать "/"
tags      := ref-name "/" tree-path
commits   := oid-or-prefix "/" tree-path
dates     := "YYYY-MM-DD" "/" tree-path
history   := repo-path "/" [ version-file ]
version-file := ( NNNN "-" short-oid | "latest" ) [ extension ] | ".truncated"
```

Две неоднозначности требуют явных правил разрешения.

**Границы имени ссылки.** В `branches/feature/login/src/Program.cs` неясно, где
кончается имя ветки. Правило: **наибольшее совпадение по списку известных
ссылок**. Список ссылок берётся из снапшота, поэтому операция дешёвая и
детерминированная. Если ни один префикс не подошёл — `NotFound`.

**Границы пути в `history/`.** Последний сегмент трактуется как файл версии
тогда и только тогда, когда он соответствует шаблону `version-file` **и**
родительский путь существует в истории как файл. Во всех остальных случаях узел
считается директорией. Это допускает существование файла с именем вида
`0001-abcdef.cs` в самом репозитории: он останется обычным файлом, потому что
его родитель — директория, а не файл.

**Неоднозначный префикс OID.** Если под префикс подходит больше одного объекта,
возвращается `NotFound`, а в `.gitfs/log.txt` пишется список кандидатов. Молча
выбирать первый нельзя.

**Нормализация.** Сегменты `.` и `..` отвергаются на этапе разбора и никогда не
доходят до резолвера.

## 5. Архитектура: слои и проекты

```
┌────────────────────────────────────────────────────┐
│ Gitfs.Cli — mount / unmount / list / doctor        │
├────────────────────────────────────────────────────┤
│ Адаптеры:  WinFsp  │  FUSE (Linux)  │  macFUSE     │  платформенное
├────────────────────────────────────────────────────┤
│ IMountTarget — Lookup / List / Open / Read / Write │  граница переносимости
├────────────────────────────────────────────────────┤
│ VirtualTree — роутинг путей по вьюхам              │
│   BranchesView TagsView CommitsView                │
│   DatesView HistoryView GitfsView                  │
├────────────────────────────────────────────────────┤
│ OverlayStore — copy-on-write песочница             │
├────────────────────────────────────────────────────┤
│ CacheSet — LRU по OID, производные индексы         │
├────────────────────────────────────────────────────┤
│ GitCore — собственный ридер                        │
│   RefStore  ObjectReader  PackIndex                │
│   LooseObjectReader  PackFile  DeltaCodec          │
│   TreeWalker  RevWalker                            │
└────────────────────────────────────────────────────┘
```

| Проект | Назначение | Нативные зависимости |
|---|---|---|
| `Gitfs.Core` | чтение git-объектов, модель истории | нет |
| `Gitfs.Vfs` | VirtualTree, вьюхи, overlay, `IMountTarget` | нет |
| `Gitfs.Mount.WinFsp` | адаптер Windows | WinFsp |
| `Gitfs.Mount.Fuse` | адаптер Linux | libfuse3 |
| `Gitfs.Mount.MacFuse` | адаптер macOS (experimental) | macFUSE |
| `Gitfs.Cli` | точка входа, разбор аргументов, `doctor` | — |

Граница `IMountTarget` («то, что монтирует адаптер») — не украшение, а условие
тестируемости: всё, что ниже неё в стеке (VirtualTree и глубже), проверяется
без единого монтирования (§17).

**Зависимости, которые надо подтвердить в начале M3/M6**, а не считать данностью:
конкретный .NET-биндинг WinFsp и его актуальная версия; библиотека FUSE для .NET
под Linux. Обе — точки риска расписания, обе проверяются одним прототипом
«смонтировать пустое дерево» до начала полноценной работы над адаптером.

## 6. GitCore

### 6.1 Модель объектов

```csharp
public readonly struct ObjectId : IEquatable<ObjectId>   // 20 байт inline, без аллокации
public enum GitObjectType { Commit = 1, Tree = 2, Blob = 3, Tag = 4 }

public enum GitFileMode { Directory, RegularFile, ExecutableFile, Symlink, Gitlink }

public readonly struct TreeEntry { string Name; ObjectId Id; GitFileMode Mode; }
public sealed class TreeObject   { IReadOnlyList<TreeEntry> Entries; }

public readonly struct Signature { string Name; string Email; DateTimeOffset When; }
public sealed class CommitObject { ObjectId Id, Tree; ObjectId[] Parents;
                                   Signature Author, Committer; string Message; }

public interface IObjectReader
{
    bool TryGetHeader(in ObjectId id, out GitObjectType type, out long size);
    Stream OpenStream(in ObjectId id);              // распакованное тело
    byte[] ReadAll(in ObjectId id, long maxBytes);
}
```

`TryGetHeader` отделён от чтения тела намеренно: `GetAttr`/`Lookup` вызываются на
порядок чаще, чем `Read`, и им нужен только размер.

### 6.2 Loose-объекты

`.git/objects/ab/cdef…` — zlib-поток, внутри `"<type> <size>\0<тело>"`.
Распаковка — `System.IO.Compression.ZLibStream` (.NET 6+), нативных библиотек не
требуется. Для заголовка инфлируется только первые ~64 байта.

### 6.3 Packfiles

**`.idx` версии 2:** сигнатура `\377tOc`, версия, fanout на 256 входов,
отсортированный массив OID, таблица CRC32, таблица 4-байтных смещений (старший
бит — признак ссылки в таблицу 8-байтных смещений для пакетов больше 2 ГБ),
контрольные суммы. Поиск — бинарный внутри бакета, выбранного по первому байту
OID через fanout.

**`.pack`:** заголовок `PACK`, версия, число объектов. Каждый объект начинается с
переменного заголовка: старший бит — продолжение, биты 6–4 — тип
(1 commit, 2 tree, 3 blob, 4 tag, 6 ofs-delta, 7 ref-delta), младшие 4 бита —
начало размера, далее по 7 бит на байт.

Пакеты открываются через `MemoryMappedFile`: ОС сама решает, что держать в
памяти, и одна проекция безопасно читается многими потоками.

### 6.4 Дельты

`OBJ_OFS_DELTA` кодирует отрицательное смещение базы, `OBJ_REF_DELTA` — её OID.
Тело дельты: размер источника (varint), размер результата (varint), затем
инструкции — копирование из базы (старший бит 1, селекторы задают, какие байты
смещения и длины присутствуют) и вставка литерала (старший бит 0, длина 1–127).

Два требования, вытекающих из формата:

* цепочка разворачивается **итеративно**, не рекурсией: реальные цепочки бывают
  в десятки звеньев;
* базовые объекты кэшируются, иначе стоимость одного чтения линейна по длине
  цепочки, а стоимость обхода директории — квадратична.

**Размер объекта под дельтой.** Размер в заголовке пакета — это размер самой
дельты, а не результата. Итоговый размер лежит вторым varint в теле дельты,
поэтому `TryGetHeader` для дельта-объекта инфлирует несколько первых байт и
кладёт результат в кэш размеров. Без этого `GetAttr` разворачивал бы всю цепочку
ради одного числа.

### 6.5 Ссылки

`.git/refs/**`, `.git/packed-refs` (включая строки `^<oid>` с разыменованными
тегами), `HEAD` и символические ссылки. Аннотированные теги разыменовываются до
коммита; `tags/` показывает дерево коммита, а не объект тега.

### 6.6 Обходы

```csharp
public interface ITreeWalker  { NodeInfo? Resolve(in ObjectId root, ReadOnlySpan<string> path); }
public interface IRevWalker   { IEnumerable<CommitObject> FirstParent(in ObjectId from); }
```

`RevWalker` идёт лениво по первому родителю. `HistoryView` поверх него сравнивает
OID блоба по интересующему пути и отбирает точки изменения.

### 6.7 Ускорители

`commit-graph` и `multi-pack-index` читаются, если присутствуют, и заметно
ускоряют `dates/` и `history/`. Оба опциональны: при отсутствии работает обычный
обход. Реализуются после M4, когда есть на чём мерить.

### 6.8 Явно вне v1

Submodules (только маркер, §3.5); гидрация Git LFS; shallow-клоны работают, но
история обрезана и `doctor` предупреждает; репозитории на SHA-256 определяются и
отвергаются понятной ошибкой, а не выдают мусор.

## 7. Кэширование и инвалидация

Свойство, на котором держится вся схема: **git-объекты адресуются содержимым и
неизменяемы**, поэтому кэш, ключом которого является OID, не нуждается в
инвалидации никогда. Инвалидировать нужно только производные от ссылок.

| Кэш | Ключ | Инвалидация | Бюджет |
|---|---|---|---|
| `ObjectCache` | OID | не требуется | доля `--cache-mb` |
| `TreeCache` | OID дерева | не требуется | доля `--cache-mb` |
| `SizeCache` | OID | не требуется | мелкий, фиксированный |
| `DeltaBaseCache` | OID базы | не требуется | доля `--cache-mb` |
| `RevisionListCache` | (OID опорной точки, путь) | при смене эпохи | по числу записей |
| `DateIndexCache` | OID опорной точки | при смене эпохи | по числу записей |
| `RefsSnapshot` | — | при смене эпохи | мал |

Вытеснение — LRU с учётом фактического размера в байтах, общий бюджет
`--cache-mb` (по умолчанию 256). Блобы крупнее порога (по умолчанию 8 МБ) не
кэшируются вовсе и читаются потоково: иначе один большой файл вымывает весь кэш.

**Эпоха.** `RepoEpoch` — счётчик, увеличивающийся при обнаружении изменений в
`.git` (по времени модификации каталога ссылок, `packed-refs` и `HEAD`, проверка
не чаще раза в секунду и только на границе операции). Смена эпохи создаёт новый
`RepoSnapshot`; кэши по OID переезжают в него как есть, производные сбрасываются.

**Исчезновение пакета.** `git gc` может удалить `.pack` под работающим
монтированием. Ошибка чтения проекции распознаётся, набор пакетов
переоткрывается, операция повторяется **один раз**; при повторном отказе —
`IoError` и запись в лог.

## 8. Модель конкурентности

Колбэки файловой системы приходят одновременно из многих потоков — это исходное
условие, а не крайний случай.

* `RepoSnapshot` **иммутабелен**. Операция читает ссылку на него один раз в
  начале и работает с ней до конца, поэтому смена эпохи в середине операции не
  наблюдается. Публикация нового снапшота — единичная атомарная запись ссылки.
* Чтение объектов не берёт блокировок: проекции пакетов и распарсенные деревья
  неизменяемы.
* Кэши — конкурентные словари с раздельными сегментами; вытеснение под
  собственной блокировкой, не пересекающейся с чтением.
* `OverlayStore` берёт блокировку на конкретный виртуальный путь, а не на
  хранилище целиком.
* Долгие построения (список ревизий, индекс дат) выполняются под
  «однократной инициализацией» на ключ: параллельные запросы одного и того же
  списка ждут первого вычислителя, а не считают его N раз.

## 9. VirtualTree и вьюхи

```csharp
public interface IView
{
    string Name { get; }
    NodeInfo?           Resolve(RepoSnapshot snap, ReadOnlySpan<string> segments);
    IEnumerable<DirEntry> List(RepoSnapshot snap, ReadOnlySpan<string> segments);
}

public enum NodeKind { Directory, File, Symlink, Submodule }

public readonly struct NodeInfo
{
    NodeKind        Kind;
    ObjectId        BlobId;
    long            Size;
    DateTimeOffset  Timestamp;
    bool            ReadOnly;
}
```

`VirtualTree` разбирает путь, выбирает вьюху по первому сегменту и делегирует ей
остальное. Вьюхи не знают ни о какой файловой системе и не имеют состояния сверх
кэшей — это делает их пригодными для тестирования как чистые функции.

Порядок применения слоёв при разрешении пути: `OverlayStore` → `VirtualTree`.
Перекрытие проверяется первым, иначе запись была бы не видна на чтении.

## 10. OverlayStore

**Расположение.** Windows — `%LOCALAPPDATA%\gitfs\overlay\<mount-id>`;
Linux/macOS — `$XDG_STATE_HOME/gitfs/overlay/<mount-id>`.

**Отображение имён.** Виртуальный путь не используется как имя файла напрямую:
он может превышать лимит длины пути и содержать экранированные последовательности.
Имя файла в оверлее — hex SHA-256 от виртуального пути; сопоставление хранится в
`manifest.jsonl` (виртуальный путь, вид записи, времена). Удаление отражается
записью-надгробием: удалённый узел исчезает из выдачи, но объект в репозитории
остаётся нетронутым.

**Область действия.** Оверлей перекрывает любую вьюху, включая `commits/`. Запись
в файл под `commits/<sha>/` видна только этому монтированию и только до
размонтирования — инвариант неизменности истории сохраняется на уровне
репозитория.

**Жизненный цикл.** Создаётся при монтировании, удаляется при штатном
размонтировании. `mount-id` включает идентификатор процесса и момент старта,
поэтому `list` и `doctor` распознают осиротевшие после аварии каталоги и
предлагают их убрать. Ключ `--keep-overlay` сохраняет содержимое.

**Видимость.** Текущее содержимое песочницы доступно только для чтения через
`.gitfs/overlay/` — пользователь всегда может увидеть, что он изменил.

## 11. Контракт IMountTarget

```csharp
public interface IMountTarget
{
    GitfsResult<NodeInfo>  Lookup(string path);
    GitfsResult<IEnumerable<DirEntry>> List(string path);
    GitfsResult<FileHandle> Open(string path, OpenMode mode);
    GitfsResult<int>       Read (FileHandle h, long offset, Span<byte> buffer);
    GitfsResult<int>       Write(FileHandle h, long offset, ReadOnlySpan<byte> data);
    GitfsResult<Unit>      Close(FileHandle h);
    VolumeInfo             GetVolumeInfo();
}

public enum GitfsError
{
    None, NotFound, NotADirectory, AmbiguousPrefix, CorruptObject,
    IoError, AccessDenied, NotSupported, TooLarge
}
```

Контракт:

* методы **не бросают исключений** — результат всегда `GitfsResult<T>` с кодом;
* `Read` может вернуть меньше запрошенного, но никогда не читает за пределами
  размера, объявленного в `Lookup`;
* хендл владеет разрешённым узлом и, при наличии, потоком оверлея; после `Close`
  использование хендла — ошибка программиста, а не пользователя;
* `List` возвращает ленивую последовательность: директория `commits/` не
  материализуется целиком.

## 12. Адаптеры

Задача адаптера сведена к трём вещам: перевести вызов ОС в вызов
`IMountTarget`, перевести код ошибки, и **не выпустить исключение наружу**.
Необработанное исключение в колбэке файловой системы вешает Проводник целиком,
поэтому каждый колбэк — внешний `try/catch` с трансляцией в код и записью в лог.

| `GitfsError` | Windows (NTSTATUS) | POSIX (errno) |
|---|---|---|
| `NotFound` | `STATUS_OBJECT_NAME_NOT_FOUND` | `ENOENT` |
| `AmbiguousPrefix` | `STATUS_OBJECT_NAME_NOT_FOUND` | `ENOENT` |
| `CorruptObject` | `STATUS_DEVICE_DATA_ERROR` | `EIO` |
| `IoError` | `STATUS_IO_DEVICE_ERROR` | `EIO` |
| `AccessDenied` | `STATUS_ACCESS_DENIED` | `EACCES` |
| `NotSupported` | `STATUS_NOT_SUPPORTED` | `ENOSYS` |
| `TooLarge` | `STATUS_FILE_TOO_LARGE` | `EFBIG` |

**Регистр имён на Windows.** Том объявляется регистронезависимым и
регистросохраняющим — как ожидают Проводник и большинство программ. Для этого при
материализации директории строится индекс по свёрнутому регистру; правило `~2`
из §3.3 гарантирует отсутствие дубликатов в этом индексе.

**Симлинки.** На POSIX — штатные `readlink`. На Windows — файл с текстом цели
(§3.5).

**Размонтирование при открытых хендлах.** Отказ с перечислением удерживающих
процессов, а не тихое зависание.

## 13. CLI и конфигурация

```
gitfs mount <repo> <target>
        [--views branches,tags,commits,dates,history]
        [--history-ref <ref>]
        [--commit-limit 200] [--history-limit 500]
        [--cache-mb 256] [--max-cached-blob-mb 8]
        [--name-policy native|portable]
        [--read-only] [--keep-overlay] [--allow-other]
        [--log <path>] [--verbose]

gitfs unmount <target>
gitfs list
gitfs doctor [<repo>]
```

`doctor` проверяет: наличие и версию драйвера ФС; права на монтирование; формат
хеша репозитория; наличие `commit-graph` и `multi-pack-index`; признаки
shallow-клона; наличие pointer-файлов LFS; осиротевшие каталоги оверлея.

Значения по умолчанию читаются из `gitfs.toml` рядом с исполняемым файлом или из
каталога конфигурации пользователя; аргументы командной строки имеют приоритет.

## 14. Диагностика

`.gitfs/status.txt` — режим монтирования, опорная точка, эпоха, попадания и
промахи кэшей, число открытых хендлов, размер оверлея.

`.gitfs/log.txt` — структурированные события: битые объекты, неоднозначные
префиксы, срабатывания правил экранирования (первое на каждое правило),
обрезание списков, переоткрытие пакетов.

Оба файла — часть смонтированного дерева, поэтому доступны без отдельного
инструмента: диагностика лежит внутри самого продукта.

## 15. Безопасность

* **Только чтение репозитория.** Ни одной мутирующей операции над `.git` на всём
  пути. Записи уходят исключительно в оверлей.
* **Ничего не исполняется.** Хуки, конфиги, `.gitattributes`-фильтры и внешние
  diff-команды игнорируются. `git`-бинарник используется только в тестах.
* **Видимость монтирования** — по умолчанию только пользователь, который
  смонтировал. `--allow-other` включает общий доступ явно.
* **Обход пути** невозможен: `..` отвергается при разборе, а резолвер вообще не
  обращается к реальной ФС, кроме каталога `.git` и каталога оверлея.
* **Оверлей** создаётся с правами только для владельца.
* **Дельта-бомбы.** Развёрнутый объект ограничен `--max-object-mb`; превышение
  даёт `TooLarge` и запись в лог, а не исчерпание памяти. Ограничивается и
  длина цепочки дельт.

## 16. Производительность: цели и бюджеты

Замеряется на прогретом кэше, репозиторий масштаба ядра git (≈1 млн объектов).

| Операция | Цель |
|---|---|
| Монтирование | < 500 мс, независимо от размера истории |
| `Lookup` / `GetAttr` | p50 < 1 мс, p99 < 10 мс |
| Листинг директории на 1000 записей | < 50 мс |
| Последовательное чтение блоба | > 100 МБ/с |
| Первое открытие `history/<файл>/` | < 2 с при 10 000 коммитов |
| Резидентная память в покое | < `--cache-mb` + 64 МБ |

Требование к монтированию — не украшение, а архитектурное ограничение: оно
запрещает любые полные обходы истории при старте. Всё строится лениво.

## 17. План тестирования

**Уровень 1 — `Gitfs.Core.Tests`.** Фикстуры собираются настоящим `git` в setup с
фиксированными автором, датой и сообщениями, поэтому OID детерминированы.
Ключевой приём — **дифференциальный тест**: для выборки объектов вывод нашего
ридера сравнивается с `git cat-file`. Эталон стоит рядом, это самая дешёвая и
самая надёжная проверка. Отдельно: длинные цепочки дельт, оба вида дельт,
пакеты больше 2 ГБ (синтетический `.idx` с 8-байтными смещениями), битые данные с
подпорченной CRC.

**Уровень 2 — `Gitfs.Vfs.Tests`.** Модель дерева как чистые функции поверх
поддельного репозитория, без монтирования: правила экранирования и коллизий обеих
политик, потолки листинга и пометка `.truncated`, резолв OID вне листинга,
неоднозначный префикс, разбор границ имени ссылки, узел, бывший и файлом и
директорией, семантика оверлея, включая надгробия.

**Уровень 3 — `Gitfs.Integration.Tests`.** Реальное монтирование на раннерах
GitHub Actions: Windows с WinFsp, Linux с fuse3. Сценарии: обход дерева, чтение,
запись в оверлей, размонтирование; `findstr`/`grep` по смонтированному дереву;
открытие одного файла двумя процессами; размонтирование при открытом хендле;
удаление пакета во время работы.

**Уровень 4 — нагрузочный.** Параллельный обход дерева из N потоков с проверкой
отсутствия гонок и утечки хендлов; сравнение резидентной памяти с бюджетом.

**Бенчмарк.** Холодный и тёплый проходы по таблице §16; результаты публикуются в
README и перепроверяются в CI на регрессии.

## 20. Риски

**macOS не проверяется локально.** macFUSE ставится расширением ядра и требует
ослабления SIP, поэтому смонтировать на macOS-раннере GitHub Actions нельзя.
Решение: код адаптера пишется, слои выше границы покрыты тестами, в README статус
обозначен как experimental с явным приглашением к тестированию. Принято
сознательно.

**Внешние зависимости адаптеров.** WinFsp и libfuse3 — сторонние компоненты;
конкретные .NET-биндинги проверяются прототипом «смонтировать пустое дерево» до
начала M3 и M6.

**Prior art.** До старта проверить фактически: `presslabs/gitfs` (Python, FUSE,
Linux/macOS — монтирует одну ветку как рабочую папку с автокоммитом, модель
принципиально иная), Microsoft VFS for Git / Scalar (виртуализация рабочей копии
больших репозиториев, не просмотр истории), существующие попытки на WinFsp.
Результат оформляется разделом README «Чем отличается» — это укрепляет проект.

**Производительность на больших репозиториях.** Снимается ленивым листингом
(§3.2), кэшами (§7) и опциональными ускорителями (§6.7). Проверяется в M7.

**Разрастание объёма.** Пять вьюх — уже много. Новые вьюхи в v1 не добавляются;
`--views` позволяет пользователю сузить набор.

## 21. Вне объёма

Запись в репозиторий и создание коммитов. Гидрация Git LFS. Submodules сверх
маркера. Сетевые репозитории. SHA-256. Графический интерфейс — кандидат в v2
(трей-иконка на Avalonia со списком монтирований).
