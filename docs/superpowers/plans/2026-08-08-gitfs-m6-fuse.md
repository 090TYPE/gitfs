# M6 — адаптер FUSE (Linux)

Дата: 2026-08-08
Спека: [§5 архитектура](../specs/2026-08-07-gitfs-design.md), §11 граница
переносимости, §19 критерий вехи, §20 риски.

Критерий вехи по спеке: **зелёный Linux-контур**. Здесь это означает не
«код компилируется под linux-x64», а том, смонтированный в Linux, на котором
проходит та же приёмка, что и на Windows.

## 0. Что уже сделано за нас

Граница `IMountTarget` — девять методов, и всё, что ниже неё, платформы не
знает вовсе. Адаптер WinFsp занимает 480 строк, из которых собственно
трансляция — треть. Значит цена второй платформы — трансляция, а не
переписывание.

Проверяемо прямо сейчас: `Gitfs.Core`, `Gitfs.Vfs` и их 197 тестов не
содержат ни одной ссылки на Windows API и собираются под `linux-x64`.
Это первая задача — не предположение, а прогон.

## 1. Выбор биндинга: почему свой

Спека (§20) требует подтвердить биндинг прототипом до начала работы.
Кандидаты:

| Вариант | Против |
|---|---|
| `Tmds.Fuse` | последний релиз 2020, таргет netcoreapp3.1; тянуть в проект неподдерживаемую зависимость ради 40 сигнатур — плохая сделка |
| `Mono.Fuse` | mono-эпоха, libfuse2 |
| **свой P/Invoke к libfuse3** | нужно вручную повторить `struct fuse_operations` |

Берём свой — по той же причине, по которой в M1 взяли свой ридер git вместо
LibGit2Sharp: одна прямая зависимость от системной библиотеки вместо
цепочки чужих, и полный контроль над тем, что происходит на границе.

**Риск свой P/Invoke — раскладка структур.** `struct fuse_operations` это
~40 указателей на функции в строго определённом порядке; ошибка в порядке
не даёт ошибки компиляции, а даёт вызов не той функции и падение ядра
операции. `struct stat` и вовсе зависит от архитектуры.

**Ответ на риск — не сверять с документацией по памяти, а спросить
компилятор.** Задача 2: крохотная программа на C печатает `offsetof` и
`sizeof` для каждого поля, которое мы собираемся использовать; её вывод
сохраняется в репозитории и сверяется тестом. Тот же приём, что с git в
M1: эталон — не наше представление о формате, а сам формат.

## 2. Задачи

| № | Задача | Готово, когда |
|---|---|---|
| 1 | Linux-контур сборки: `Gitfs.Core`, `Gitfs.Vfs` и тесты под linux-x64 в контейнере | 197 тестов зелёные в Linux |
| 2 | ABI-проба: C-программа печатает раскладку `fuse_operations`, `stat`, `fuse_file_info`, `statvfs`; вывод — фикстура | фикстура в репозитории, значения совпали с нашими константами |
| 3 | Прототип «пустое дерево»: смонтировать каталог с одним файлом через свой P/Invoke | `ls` и `cat` в контейнере видят его |
| 4 | `Gitfs.Mount.Fuse`: getattr, readdir, open, read, release, statfs | том с пятью вьюхами читается |
| 5 | Запись: create, write, truncate, unlink, utimens поверх overlay | приёмка проходит сценарии записи |
| 6 | Трансляция `GitfsError` → `-errno`, тесты как у NTSTATUS | таблица покрыта тестами |
| 7 | `tools/acceptance.sh` — те же 26 сценариев | 26/26 на смонтированном томе в Linux |
| 8 | CLI и приложение: выбор адаптера по платформе, `doctor` для Linux | `gitfs mount` работает без ключей |

## 3. Решения, принятые заранее

**Высокоуровневый API, а не низкоуровневый.** `fuse_lowlevel` оперирует
инодами и требует собственной таблицы имён; высокоуровневый оперирует
путями — ровно тем, что принимает `IMountTarget`. Низкоуровневый быстрее,
но у нас узкое место не в этом (§16 показал: история, а не диспетчеризация).

**`fuse_new` + `fuse_mount` + `fuse_loop`, а не `fuse_main`.** `fuse_main`
блокирует поток и сам разбирает argv — приложению с кнопкой «Смонтировать»
это не подходит. Раздельные вызовы дают ту же модель, что у WinFsp:
смонтировать, крутить цикл в фоне, снять по требованию.

**`-o default_permissions` и `-o ro` по умолчанию.** Права считает ядро по
тем `st_mode`, что мы отдаём; режим только на чтение снимается ключом,
как на Windows.

**Один процесс — один том, `foreground`.** Демонизация (`-f` наоборот)
отдана вызывающему: CLI держит процесс, приложение держит поток.

## 4. Чего в M6 нет

* macOS (macFUSE) — веха M8, и она непроверяема локально (§20).
* Симлинки как настоящие `readlink` — спека §207 разрешает, но это меняет
  поведение вьюх; выносится отдельно, чтобы не смешивать с адаптером.
* Расширенные атрибуты: `setxattr`/`getxattr` возвращают `ENOTSUP`.

## 5. Результат

Веха закрыта. Критерий «зелёный Linux-контур» выполнен буквально:

```
81 + 118 + 76 = 275 юнит-тестов
28/28 сценариев приёмки на смонтированном томе — дважды подряд
том и песочница исчезают по SIGTERM
```

Прогоняется одной командой с любой машины, где есть docker:

```bash
tools/linux-check.sh
```

### Что нашла проба ABI

Три места, где «очевидная» раскладка неверна и ошибка не дала бы ни одного
предупреждения компилятора:

* в `struct stat` поле `st_nlink` лежит **перед** `st_mode` (16 против 24) —
  восьмибайтное поле раньше четырёхбайтного;
* `fh` в `struct fuse_file_info` на смещении 16, а не 8: перед ним битовое
  поле с выравниванием;
* `utimens` — 256-й байт таблицы операций, а не 248-й: между `create` и
  `utimens` стоит `lock`.

### Что нашло живое монтирование

**`O_TRUNC` обязан отрабатывать адаптер.** Ядро согласует атомарное
усечение и отдельного `setattr(size=0)` не присылает — оно кладёт флаг в
`open`. Пока адаптер флаг только читал (чтобы выбрать режим), но не
усекал, `echo x > файл` писал пять байт в начало и оставлял хвост:
файл на 1073 байта после перезаписи оставался на 1073 байта. Ни один
юнит-тест такого не увидел бы: ошибка живёт в договоре с ядром.

**Удалённый файл из репозитория нельзя было создать заново.** Надгробие
песочницы проверялось до выбора режима, и `Open(path, Write)` получал
«файла нет» вместо создания. «Удалить, затем записать на то же место» —
не экзотика, а способ сохранения у половины программ; для файлов из
песочницы это работало, для файлов из репозитория — нет, и путь оставался
мёртвым до конца жизни тома. Дефект общий для обеих платформ, найден на
Windows, закрыт в `VfsMountTarget` — ниже границы, то есть сразу для обеих.

### Что нашла сама приёмка

**Она не выдерживала повторного запуска.** Сценарии записи трогали те же
файлы, что читают проверки чтения, и второй прогон по тому же тому
обвинял том в следах первого. Набор, который можно запустить один раз, —
ловушка: он скрывает ровно те дефекты, что живут в повторном
использовании (пересоздание после удаления и нашлось именно так).
Теперь чтение и запись разведены по разным файлам, а Linux-контур
прогоняет приёмку дважды подряд.

**Проверка «репозиторий не изменён» была написана неверно** — она требовала
чистого `git status`, а не отсутствия изменений от тома. На рабочей копии с
правками она падала, ничего не сообщая о томе. Теперь сравнивается
состояние до и после.

**Эталоном служил файл на диске, а не git.** Том отдаёт содержимое
репозитория, и рабочая копия законно отличается от него — например
переносами строк после нормализации. Дополнительно выяснилось, что
`git cat-file blob > файл` в PowerShell 5.1 непригоден для сверки:
оболочка перекодирует вывод нативной команды в UTF-16 и меняет переносы,
превращая 1073 байта в 2190. Сверка идёт по SHA, который считает git.

## 6. Адверсариальное ревью

Шесть независимых линз по адаптеру и работе с песочницей, каждая находка
проверялась отдельным агентом с заданием её **опровергнуть**. Выжило
одиннадцать; все закрыты, каждая с тестом. Полный разбор — в коммите
`8047acb`, здесь только то, что стоит помнить.

**Самое дорогое стоило одной строки.** Аренда снапшота отпускалась дважды —
и том зависал навсегда, вместе со всеми процессами, которые к нему
прикоснулись. Инвариант «взята один раз, отпущена один раз» стоял в спеке
§8 и не проверялся нигде. Соглашения недостаточно там, где цена ошибки
несоразмерна её размеру: аренда стала классом с флагом, и нарушить её
теперь нельзя, а не «не следует».

**Зелёные тесты доказывали меньше, чем казалось.** Сборка под `linux-arm64`
проходила целиком, хотя раскладка структур там другая и адаптер писал бы
мимо полей: проверка архитектуры читала утверждение фикстуры о самой себе,
а не архитектуру процесса. Тест, который спрашивает у данных, верны ли
данные, — не тест.

**Ускоритель мог уронить монтирование.** Один перевёрнутый бит в
`commit-graph` — и репозиторий не открывался вовсе, из-за файла, который
по определению необязателен. Отсюда правило: необязательное не имеет права
ломать обязательное ни при каком содержимом.

**Четыре системные слабости**, которые ревью назвало отдельно:

1. Никто не владел временем жизни потока цикла FUSE — снос шёл по таймауту
   и результат ожидания отбрасывался.
2. Владение арендой держалось на соглашении, а не на типе.
3. Песочница завела собственное представление о путях (регистр, надгробия,
   усыновление файлов) вместо того, чтобы взять его у слоя вьюх — три
   независимых дефекта данных выросли ровно отсюда.
4. Данные репозитория разбирались как заведомо корректные: проверить начало
   и потом читать — привычка, давшая и переполнение стека, и падение на
   битом графе.

### Долг

| Что | Почему отложено |
|---|---|
| Надгробия на поддерево | сейчас удаление директории отказывает целиком. Честно, но `rm -rf` всё равно успевает пометить файлы внутри, прежде чем упереться в саму директорию |
| Шесть проверок приёмки, которые не могут упасть | «tags view is reachable» возвращает успех безусловно; «version content equals git cat-file» сравнивает размеры, а не байты; «missing path is reported missing» не смотрит на errno. Пока они такие, зелёный прогон — слабое свидетельство |
| `ErrnoTranslationTests` проверяет `code > 0` | catch-all `_ => Errno.IO` удовлетворяет этому всегда; заявленная цель теста — заметить новый `GitfsError` без перевода — как раз и не достигается |
| Старт потока в конструкторе `GitfsFuseMount` | если `Thread.Start` бросит (исчерпан лимит процессов), утечёт всё, а том останется в таблице монтирования без обслуживания |
| Перечитывание `commit-graph` на каждую смену эпохи | граф иммутабелен и по содержимому не зависит от движения ссылок, но перечитывается целиком под замком |
| `IncludeAllContentForSelfExtract` включено безусловно | обоснование относится только к winfsp.net; под Linux самораспаковка не нужна и мешает контейнерам с read-only ФС |
| `fuse_loop_mt` вместо `fuse_loop` | цикл однопоточный: операции сериализованы. Раскладка `fuse_loop_config` менялась внутри 3.x, а выигрыш надо сперва обосновать — на однопоточном цикле чтение уже даёт 827 МБ/с через ядро, то есть узкое место не здесь |
